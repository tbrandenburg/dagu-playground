# Verification and screenshot provenance

## Reproduce the acceptance checks

```sh
make check
make test-scale
make test-lifecycle
git diff --check
```

The expected results are:

- Ruff lint and formatting checks pass; Prettier reports no formatting changes.
- Seven tooling tests pass against actual local HTTP requests and validated argument boundaries.
- Six workflow files pass the pinned `dagu validate` command.
- The default demo completes eight successful DAG runs across two workers and the local server.
- The negative acceptance checks confirm a failed missing-file step, an unstarted dependent step, a rejected invalid step ID, and an HTTP 404 for an unknown workflow.
- Scaling to one and three workers permits successful distributed runs and returns to the original worker count.
- Recreating the stack retains eight successful run records, their worker provenance, returned worker logs, and a server log after the worker containers are gone.

The intentional `expected-failure` DAG is expected to be red in the dashboard. The acceptance command itself must exit zero only after checking that behavior.

## Compatibility discoveries tested during setup

1. **Read-only workflow mounts:** startup initially failed because the default Wiki path is beneath the DAG directory. Moving `DAGU_WIKI_DIR` to the server volume fixes initialization without making tracked workflows writable.
2. **Workflow schema:** this release rejects root `name` and hyphenated step IDs. Names come from filenames; step IDs use underscores.
3. **String steps are valid:** a list of command strings is valid Dagu shorthand, not an invalid-schema fixture. The negative test uses a genuinely invalid step ID instead.
4. **Dispatch versus queueing:** the immediate `/start` endpoint has a bounded dispatch wait. Submitting extra work while deliberately saturating capacity hit that deadline during repeated testing. The demo now finishes its held distribution batch before submitting the other scenarios, without masking or retrying failed submissions.
5. **Returned logs persist:** worker stdout can be read through the server even after deleting and replacing the original worker containers. The lifecycle check verifies this explicitly.

## Scope and limitations

Local verification uses Linux amd64, Docker Engine 29.9.2, Compose 5.6.1, and Dagu 2.22.2. The image manifest also advertises Linux arm64 and arm/v7; those architectures were not executed here. GitHub CI repeats the acceptance commands on a fresh Linux runner; its authoritative status is the linked [workflow run history](https://github.com/tbrandenburg/dagu-playground/actions/workflows/ci.yaml), not this static document.

Browser console connection errors observed during the lifecycle test corresponded to the intentional server down/up window. The dashboard loaded again and a UI-triggered workflow succeeded afterward.

To refresh the screenshot, run `make demo`, open `/dag-runs`, confirm successful rows show two worker IDs, capture the viewport under `docs/images/`, and update this document with the new report's timestamp and run IDs. Keep generated reports in ignored `.artifacts/`, not in the repository.
